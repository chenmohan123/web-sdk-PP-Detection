# PP-YOLOE+ M/L/X 三精度桌面对比

日期：2026-09-14。比较同一规格的 FP32、FP16 和 W8A32，文件缩小单独计为收益。基线是已发布的 M/L/X 0.1.0 FP32，SDK 0.4.0；本轮不修改 SDK API。

## 评测范围与口径

- 固定 COCO val2017 子集 64 图、716 个标注，注释 SHA-256 为 `d398fc9b09d97135e9b92d28d170681ed50bcd3a5518f16f559e6e379adc1b79`。图片字节由既有 `images.lock.json` 校验。此子集用于回归比较，不能当作全量 COCO 成绩或泛化精度排名。
- 每规格分别执行 Python ONNX Runtime CPU、浏览器 WASM、WebGPU 三种后端，所有推理串行执行。Python 使用 OpenCV INTER_CUBIC、4 线程；浏览器使用 SDK bicubic、WASM 单线程、main 模式，关闭缓存和后端回退。
- 每种精度只与相同规格、相同后端及预处理的 FP32 对照。Python 与浏览器的图片缩放实现不同，不直接跨两者逐框比较。
- 同时报告 score≥0.5 下的同类一对一框匹配：IoU≥0.99 为严格坐标一致性，IoU≥0.5 为常规识别保留率；另外计算 COCO AP、增减框和最大分数/坐标差。
- 本轮沿用 L 既有评估的严格候选门槛：AP 下降≤0.5 个百分点、IoU≥0.99 下保留≥95%的 FP32 框。历史 S/PicoDet 稳定精度发布采用 IoU≥0.5 的识别门槛，两者不同。严格未达标不等于模型无法正确识别；本轮保留两种结果，不根据本次结果自动降低门槛。
- 本轮每组合运行一次完整 64 图。通过质量初筛也只进入候选，稳定发布仍需重复运行、Worker 生命周期、双源分发及 Demo 验证。未通过初筛者保留 labs 证据。

## 转换与身份

FP16 保留默认敏感算子与 ReduceMean 的 FP32 边界，浮点输入输出保持 FP32；W8A32 将 Conv 权重按通道 INT8 存储，反量化后执行 FP32 卷积，激活为 FP32，SDK 中对应 `precision=int8`、`quantization=weight-only-int8-activation-fp32`。W8A32 的文件压缩不代表使用整数卷积加速。

`jobs.json` 固定九组模型的字节数、SHA-256 与本地实验清单，六份 `*-conversion.json` 固定转换版本、输入摘要和输出摘要。L 的两个产物摘要与 2026-09-13 原实验相同，本轮新增同口径完整浏览器对照。

来源为 PaddleDetection 固定提交 `b25522a0f4bde8c80603f3ba5e3472059972e3b5` 的 PP-YOLOE+ 模型；许可、上游权重与 FP32 分发依据见 [S/M/L/X 发布证据](../../distribution/2026-09-14-ppyoloe-smlx/README.md)。ONNX 大文件仅存本地工作目录，不进入 Git 或 npm。实验清单的 localhost 地址不属于公开下载源。

FP16 的常规识别保留率为 99.21%–100%，W8A32 为 97.43%–99.63%；六变体所有后端的 AP 最大下降为 0.348 个百分点。六变体均通过历史 S/PicoDet 的单轮识别质量口径，但不满足本轮 IoU≥0.99 的严格候选门槛。原始增减框、分数差和坐标差见 `summary.json`。

WASM 热推理在同规格三种精度之间接近；WebGPU 的 L/X FP16 本轮略快、M FP16 接近，W8A32 本轮均略慢。只把它们作为一次运行观察，体积缩小是此次明确可计的收益。

## 运行环境与耗时边界

Windows 11（10.0.26200）、Intel Core i5-10400F（12 逻辑线程）、NVIDIA Blackwell 物理适配器、Chromium 153.0.8010.12、ONNX Runtime Web 1.27.0。Python 为 3.11.15、ONNX Runtime 1.20.1、ONNX 1.16.2、NumPy 1.26.4、OpenCV 4.11。

文件体积使用十进制 MB；AP 使用 0–100。热推理耗时取排除首张后的 63 图中位数，只反映本次运行，不宣称稳定加速。会话创建、首图、热端到端中位数和 P90 保存在 `summary.json`。输入模型来自本机 HTTP 并以字节传给 SDK，不含公网下载；测试工具的 JPEG 预取也不计入 SDK 的单图耗时。

实际 WebGPU 后端与物理适配器已记录；ORT 允许将部分 shape 等算子分配给 CPU，这与关闭 SDK 后端回退是不同层面的行为。此轮没有重复手机、其他浏览器或峰值内存测试，模型文件缩小不能直接推导内存同比缩小。

## 复现与证据核验

在 SDK 根目录使用已有 Python 环境，先按 2026-09-11 的图片锁准备本地图片，并准备 `jobs.json` 对应的三个固定 FP32 源模型。`prepare` 会逐一核验源模型与图片摘要，生成六个精度产物及九份本地实验清单。

```powershell
$env:PYTHONIOENCODING = 'utf-8'
$precisionPython = '.tmp/phase2/venv/Scripts/python.exe'
& $precisionPython reports/evaluation/2026-09-14-ppyoloe-mlx-precision/evaluate.py prepare
pnpm build
node reports/evaluation/2026-09-14-ppyoloe-mlx-precision/browser.mjs
& $precisionPython reports/evaluation/2026-09-14-ppyoloe-mlx-precision/evaluate.py python
& $precisionPython reports/evaluation/2026-09-14-ppyoloe-mlx-precision/evaluate.py archive
& $precisionPython reports/evaluation/2026-09-14-ppyoloe-mlx-precision/summarize.py
```

复算质量指标仅需最后一条命令、现有 Python 评测依赖与仓库内压缩证据，无需下载模型或图片。`artifact-index.json` 记录每份原始 JSON 与 gzip 的摘要，汇总先核验原字节，再验证模型、实验清单、图片集、运行时和同组身份。Python 的单独预测文件与运行报告通过 `*-python-binding.json` 共同绑定到输入、推理脚本和 Python/ORT/OpenCV/NumPy 版本，防止复用错配的旧结果。缺少绑定的历史输出重新推理后生成记录。

## 本轮决策与下一阶段

六个精度产物均完成转换、9 组 Python 与 18 组浏览器的完整 64 图评测，归档可独立复算。本轮六变体全部保留 labs，不上传新的权重、不进入稳定清单或 Demo；npm 保持 0.4.0。这里的暂缓原因是严格坐标一致性不足，不能表述为识别功能失效或文件压缩没有价值。

下一阶段应先统一精度变体的发布目的与质量口径：若目标是保持目标识别、接受少量坐标变化，历史 S/PicoDet 的 AP+IoU≥0.5 口径与此目标更接近，本轮六变体均有进入重复验证的价值；若应用要求框位置接近 FP32，继续使用 FP32，并另行研究误差控制。门槛应在下一批验证前明确，不用改写历史结果来追认通过。

按已确认口径进入稳定候选后，还需同一固定样本三轮复现、main/Worker 生命周期、固定 ModelScope/Hugging Face 分发回读和生产 Demo 验证。体积收益足以成为发布理由，不额外要求必须比 FP32 更快；扩大到全量 COCO 或业务样本可增强识别泛化证据。本轮不安排无针对性的 FP32 节点保留扩张，也不因桌面结果增加手机兼容声明。
